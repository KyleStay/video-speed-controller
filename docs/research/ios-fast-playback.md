# iPhone Safari playback above 2×: primary-source research

Research date: 2026-10-26. The source investigation and measurement plan below are separate from the bounded physical-device results recorded afterward. WebKit source claims are pinned to upstream commit [`15ab57a66f90f805ad8c8b6f42c9a54a8158ab2f`](https://github.com/WebKit/WebKit/commit/15ab57a66f90f805ad8c8b6f42c9a54a8158ab2f) (commit metadata: 2026-10-26T18:26:49Z); it does not establish which changes ship in the connected phone's Safari build.

## Findings

**The existing HLS-to-MP4 transition addresses a real platform mechanism, but cannot guarantee smooth video or uninterrupted audio above 2×.** Separate three questions in the physical test: did the original video actually switch to the supplied MP4; is its media clock advancing at the requested rate; and are picture and sound delivered continuously?

### Documented behavior and limits

1. Apple's [QA1772](https://developer.apple.com/library/archive/qa/qa1772/_index.html), dated 2016-03-23, distinguishes 1–2× playback from fast-forward capability above 2×. File-based assets can report fast-forward capability once ready, but Apple explicitly warns that bandwidth or processing load at higher rates can cause degraded playback, including I-frame-only decoding/display. Therefore MP4 availability and setter acceptance are not smoothness guarantees. This is an AVFoundation document, not a promise about every Safari implementation.

2. WebKit's [HLS rate-limit change](https://github.com/WebKit/WebKit/commit/d1cf1ce59abb8c7e1a1f64efdeb4f50d8c9f83ce) explicitly describes native HLS above 2× entering I-frame-only mode. Without an I-frame variant, the engine can accelerate using pause/seek/play cycles, causing audio stutter. Its remedy is a **site-specific HLS 2× cap**, not a global HTMLMediaElement limit. The [current implementation](https://github.com/WebKit/WebKit/blob/15ab57a66f90f805ad8c8b6f42c9a54a8158ab2f/Source/WebCore/html/HTMLMediaElement.cpp#L4457) still contains a quirk-gated HLS cap. Its playback-rate getter exposes the stored requested rate after any cap. It also forwards a setter call to a potentially playing native player before checking whether the requested value changed. Repeated equal assignments can therefore still reach the native engine; counting only `ratechange` events can miss those assignments.

3. Apple's [HLS authoring specification, Trick Play section](https://developer.apple.com/streaming/hls-authoring-specification-for-apple-devices.html) requires I-frame playlists for scanning/scrubbing and recommends dense I-frame renditions. That is a publisher packaging capability. An extension cannot create a valid same-asset I-frame rendition merely by changing an HTML property. The specification does not promise ordinary full-frame playback with continuous audio at arbitrary accelerated rates.

4. The [HTML standard](https://html.spec.whatwg.org/multipage/media.html#dom-media-preservespitch) defaults `preservesPitch` to true; false permits pitch to change with playback speed. It provides no JavaScript selector for AVFoundation's spectral versus time-domain algorithm. The standard requires rate and pitch changes without perceptible gaps, but that requirement is not evidence that a specific Safari build meets it.

### Pitch correction: avoid an obsolete 2× explanation

Current Apple documentation describes [timeDomain](https://developer.apple.com/documentation/avfoundation/avaudiotimepitchalgorithm/timedomain?changes=_4%2C_4%2C_4%2C_4) as less computationally expensive than spectral and supporting variable rates from 1/32 to 32. [spectral](https://developer.apple.com/documentation/avfoundation/avaudiotimepitchalgorithm/spectral?changes=_6__8%2C_6__8%2C_6__8%2C_6__8) also supports 1/32–32, at greater computation cost. [varispeed](https://developer.apple.com/documentation/avfoundation/avaudiotimepitchalgorithm/varispeed) supports 1/32–32 without pitch correction. The deprecated [lowQualityZeroLatency](https://developer.apple.com/documentation/avfoundation/avaudiotimepitchalgorithm/lowqualityzerolatency) instead snaps to a list ending at 2×. An [archived Apple guide](https://developer.apple.com/library/archive/documentation/AudioVideo/Conceptual/AVFoundationPG/Articles/04_MediaCapture.html) gives the older time-domain range of 0.5–2×; it conflicts with current documentation and must not be used as a current blanket ceiling.

Upstream WebKit's [Cocoa preferences](https://github.com/WebKit/WebKit/blob/15ab57a66f90f805ad8c8b6f42c9a54a8158ab2f/Source/WTF/Scripts/Preferences/UnifiedWebPreferences.yaml#L4892) select `BestForSpeech` by default. Its [algorithm mapping](https://github.com/WebKit/WebKit/blob/15ab57a66f90f805ad8c8b6f42c9a54a8158ab2f/Source/WebCore/platform/audio/cocoa/MediaSessionManagerCocoa.mm#L250) maps that to timeDomain when pitch correction is active, BestAllAround/BestForMusic to spectral, and disabled pitch correction (or rates 0/1) to varispeed. The [AVFoundation bridge](https://github.com/WebKit/WebKit/blob/15ab57a66f90f805ad8c8b6f42c9a54a8158ab2f/Source/WebCore/platform/graphics/avfoundation/objc/MediaPlayerPrivateAVFoundationObjC.mm#L1716) updates the native item's algorithm when setting rate or `preservesPitch`. Consequently `preservesPitch=false` is a useful controlled experiment that changes an actual engine path. It changes the user's sound and is not a transparent fix; improvement would support an algorithm-dependent problem, not prove a documented 2× limit.

Apple's [AVSampleBufferAudioRenderer documentation](https://developer.apple.com/documentation/avfoundation/avsamplebufferaudiorenderer/audiotimepitchalgorithm?changes=la_9_8___7__5_7&language=objc) says unsupported algorithm rates may mute audio and changing algorithms during playback may briefly set the rate to zero. This concerns that renderer API; do not infer that a normal progressive-video AVPlayer uses its documented default or that Safari necessarily mutes above 2×.

### Relevant first-party bug evidence

- [WebKit bug 163433](https://bugs.webkit.org/show_bug.cgi?id=163433), still NEW when read, reports a brief playback interruption when changing `playbackRate`, with later iOS reports. It supports testing transitions separately from stable playback; reports do not establish the cause of continuous dropout on the connected phone.
- [WebKit bug 240405](https://bugs.webkit.org/show_bug.cgi?id=240405) reports choppy audio and ignored pitch policy when a media element is connected through `createMediaElementSource`. It is RESOLVED FIXED, with a March 2026 upstream landing. That does not prove availability in an installed Safari version. Creating a Web Audio source merely to measure the problem can change the pipeline under test; avoid it for the initial baseline.

## Gaps in the current workaround

Code inspected: `src/site-handlers/base-handler.js` (the narrow `handleSpeedChange` method), `src/core/safari-hls-playback.js`, `src/site-handlers/progressive-media-source.js`, `src/site-handlers/twitter-media-source.js`, and the playback-above-2× section of `docs/safari.md`.

- Switching is conditional on iOS/native HLS, finite duration, readiness, same-video/source identity, acceptable tracks, and presentation state. An absent or rejected candidate intentionally leaves HLS active. Numeric speed alone cannot reveal which path ran.
- The general resolver chooses the largest supplied rendition up to 720p, then a smaller known higher-resolution rendition when no capped candidate exists. The X resolver prefers the largest supplied rendition up to 720p and higher bitrate ties. Neither decision models requested speed, frame rate, codec/profile, measured decode capacity, audio continuity, or thermal state. A 720p60 rendition at 4× can impose a different workload than 720p30.
- `BaseSiteHandler.handleSpeedChange` already guards `video.playbackRate !== speed` before writing. Redundant setters are a platform diagnostic consideration, not an established unfixed StayFast bug. Require an actual setter trace before proposing a product change on that basis.
- Once already progressive, the HLS coordinator does not choose a cheaper progressive rendition. Thus a successful initial MP4 switch is not an adaptive decode solution, and initially progressive videos are outside this workaround.
- Source/track/DRM/ad/live exclusions preserve ownership and media semantics. Relaxing them would not fix the native pipeline and could lose captions, audio choices or protected playback.

These are implementation observations and hypotheses to test, not evidence that a particular gate or rendition caused the reported failure.

## Physical-device experiment and falsifiable next steps

Use a neutral synthetic clip with continuous speech or tone, moving frame numbers/timecode, and separately supplied same-content HLS and MP4 renditions. Run on the connected iPhone with the exact OS/Safari/extension versions recorded. Compare extension disabled and built extension enabled on the same clip. Measure stable windows at 1×, 2×, 2.1×, 2.5×, 3× and 4×; separate warmup/rate-change/source-switch time from at least ten seconds of steady playback. Repeat a failure after cool idle time and reverse rate order to expose order-dependent behavior.

Record `currentTime` change divided by monotonic wall time, requested/read-back rate, `paused`, `seeking`, readiness, buffered-ahead duration and event timestamps. Use `requestVideoFrameCallback` to collect media PTS, callback gaps, `presentedFrames` deltas and optional processing duration. The [API specification](https://wicg.github.io/video-rvfc/) describes compositor submissions, not a guarantee of every decoded frame: callback frequency is capped by the browser's rendering rate, and main-thread load can skip callbacks. Compare gaps and presented-frame counter deltas; do not require source-fps × speed callbacks when that exceeds display cadence.

**Audio needs its own proof.** A muted flag, resolved Play promise, advancing media time and high video callback rate cannot establish audible continuity. Use an authorized external audio recording or explicit live listening observation of the synthetic continuous track, with timestamps correlated to the measurement windows. Keep “audible, not quantitatively captured” separate from measured dropout duration. Do not insert `createMediaElementSource` in the baseline just to acquire samples.

The lowest-risk implementation path is to first prove the actual source and redundant-operation behavior, then test lower supplied progressive renditions and pitch policy independently. A universal 2× cap, automatic pitch change, extra fetch/transcoding pipeline, or relaxed source safety gates is not justified by these sources or by prior setter/cadence-only success.

## Independent retrieval verification

The current time-domain rate range was independently checked through a read-only HTTPS GET of Apple's [official DocC JSON content](https://developer.apple.com/tutorials/data/documentation/avfoundation/avaudiotimepitchalgorithm/timedomain.json), parsed in memory with Python `urllib.request` and `json.load` (no browser capture). Its `primaryContentSections` → content → Discussion says: “uses a variable rate from `1/32` to `32`.” The declaration's platform list includes iOS and iPadOS. This verifies what current documentation states; it is not a measurement or guarantee of the phone's engine.

The public [GitHub commit API](https://api.github.com/repos/WebKit/WebKit/commits/main) supplied the SHA above. The HTMLMediaElement setter, Cocoa preference, algorithm mapper and AVFoundation bridge were then read from `raw.githubusercontent.com` using that exact SHA and checked again before replacing moving links with immutable source links.

## Physical iPhone comparison — October 26, 2026

The wired iPhone 15 Pro Max reported iOS 26.7.1 through CoreDevice; its Safari user agent reported Version/26.6.2 and a frozen iPhone OS 18_7 value. A development-signed **0.11.6 (29)** was installed for this device. Its 25 extension resources matched the frozen TestFlight 29 resource hashes. Production JavaScript was unchanged for the baseline and original rendition-fixture comparisons below. Qorvex supplied genuine device taps after the phone's UI Automation gate became available; later live-site checks used the repository's background XCTest fallback after Qorvex sessions stalled.

A generated 640×360/30fps H.264/AAC clip with a continuous 997Hz tone was served as MP4 and remuxed into four-second native-HLS segments, without an I-frame rendition. A closed shadow root kept the baseline video outside StayFast's controller. Each reported sample used a trusted rate-selection tap, one second of warm-up and eight seconds of frame-callback/media-clock measurement. The video was unmuted with pitch preservation enabled; **audio continuity was not recorded or independently verified**.

| HLS           | 4×             | 3.50×                  | 1.75                | 1436ms           | 1436ms               |

The HLS measurements ran in the order 4×, 2×, 2.1×. Above 2×, repeated native waiting/playing events and large media-time jumps accompanied the sparse picture updates; the requested-rate getter alone concealed that behavior. The MP4 sample had no waiting/pause events during its measurement window. Buffering differed between formats, so this is evidence of native HLS degradation on this phone, not a universal throughput or smoothness guarantee. No repeated JavaScript load/seek/play loop drove the baseline. An earlier automatically sequenced run paused unexpectedly and was excluded; later interrupted/ended-clip attempts were also retained separately, not counted as passing samples.

The existing public X rendition fixture was then exercised with its nearby accessory variants and 1080p download declaration, using an unmuted local copy. Content blocking initially prevented its CDN media from loading. Temporarily turning off content blockers for the local fixture allowed playback; the original setting was restored afterward. This does not establish that content blocking causes the reported live-feed problem.

The unchanged extension selected the explicitly supplied same-clip 720p MP4 at 2.1× and 4×. The five-second measurement windows recorded 2.10×/56.19 callbacks/sec and 4.00×/59.80 callbacks/sec respectively, with the original video, scroll offset and playing state retained and no reported errors. A subsequent clip inherited 4× and selected MP4 (4.00×/59.59 callbacks/sec; original Play promise resolved). ## Authenticated X source diagnosis

After the user signed in, the original public post was tested on the same phone. At 2.1× it retained native HLS, rejected the progressive candidate and produced 3.8 frame callbacks/sec with a 782ms maximum gap and repeated waiting/playing events (`live-threshold.json`). This reproduced the picture failure on a live post rather than a local fixture.

The current X player exposes renditions in `videoComponent` React props at `children[1].props.playerState.tracks`. Its selected track is bound by `source.trackId` and `currentTrackId`; the observed IDs are numeric zero. The older resolver did not read that path. The playing HLS URL also appends `variant_version=1`, while the SDK's selected HLS variant retains the base URL. Strict string equality rejected that pair even after finding its metadata. `isPreview=true` and `adLoaded=true` occur on the ordinary inline clip and do not by themselves identify an advertisement or a restricted preview.

The candidate reads only that bounded, directly observed SDK slot and its uniquely selected current track. It requires explicit no-caption declarations, finite duration, ordinary media without a declared availability restriction, native stream eligibility and supplied same-asset HTTPS variants. It permits only the observed single transport marker when the selected HLS variant otherwise matches exactly; other query differences, changed variants, captions, DRM/ad/live declarations and ambiguous items remain rejected. The expanded viewer omits availability for the same clear current track; that absence is accepted, while an explicitly unknown/unavailable declaration or accessor is rejected. SDK vetoes apply before older React/HTML fallback. It never calls player APIs or constructs/fetches rendition URLs.

A local development build with this resolver and a temporary measurement interface was installed. The interface read source/cadence and could reveal the existing transport for native accessibility taps; it did not drive playback, change pitch or select sources. Genuine StayFast speed/play/seek taps produced these results on the original clip in the normal inline feed:

| Source after selection | Requested rate | Window | Media-time / wall-time | Frame callbacks/sec | p95 gap | Maximum gap |
| ---------------------- | -------------- | ------ | ---------------------- | ------------------- | ------- | ----------- |
| Supplied 720p MP4      | 2.1×           | 5.00s  | 2.1005×                | 46.00               | 34ms    | 166ms       |
| Supplied 720p MP4      | 4×             | 3.00s  | 4.0011×                | 47.32               | 33ms    | 167ms       |

Both measurements retained the same clip's MP4 before and after the window, with no media errors; the 4× window had no waiting events. The shorter 4× window avoids the end of this 20.4-second clip. Receipts are `gate4-measured.json` and `normal-feed-4-r3.json`. Earlier automation attempts navigated into X's immersive feed or selected a different captioned clip; they remain separate and are not passing comparisons. Captioned feed media correctly retained HLS.

This fixes a concrete source-resolution failure. It does not prove every X clip is eligible, continuous audio, or perfect frame delivery. First-network-request MP4 selection is also not established: X initially chooses HLS, and StayFast validates its loaded stream and current metadata before selecting a supplied MP4. Saved/session fast speeds use the existing bounded initialization path; no capability spoofing or global request interception was added.

The expanded-viewer follow-up on the same post found the omitted availability field described above. With that case accepted, a contiguous native navigation → site viewer → genuine speed/seek flow selected and retained the same MP4. After waiting for the timeline to advance beyond two seconds, its five-second steady window measured 2.1003× progress, 53.79 frame callbacks/sec, 33ms p95 and 51ms maximum gap, with no waiting events or media errors and audio unmuted. `viewer-steady-2.1-r4.json` retains this result. An earlier immediate post-seek window measured 1.99× and was superseded by this settled measurement. Runs that accidentally observed a later immersive-feed clip are not acceptance evidence.

## Independent captured audio on the iPhone

Two microphone-off system recordings compared the same generated H.264/AAC tone clip on the physical phone. The first captured native MP4 at 4× and native HLS at 4×. A second supplied the HLS 2× positive control followed by HLS 4×. Pitch preservation remained enabled. The original test video's audio graph was unchanged.

The recordings stayed on the phone. Safari decoded the selected task recording locally at 48kHz/stereo; a content security policy blocked network connections. Analysis computed RMS in 10ms bins, treating RMS below 0.001 as silent and projecting 500ms summary windows. Only those numeric summaries were read through native accessibility. This measures captured app audio, rather than acoustic speaker output or subjective sound quality.

The MP4 4× recording had zero silent bins throughout the steady 5.5–17.0s recording interval, with RMS about 0.011. The HLS 2× control likewise had zero silent bins at 5.0–15.5s. HLS 4× was silent through its steady intervals in both recordings. Control-center/navigation/warmup boundaries were excluded. The positive HLS 2× sample establishes that this recording path can capture this same stream's audio; the silence is rate-dependent, rather than a blanket HLS capture limitation.

The concurrent eight-second media measurements recorded MP4 4× at 4.0001× progress/58.85 frame callbacks per second, HLS 2× at 2.0002×/57.74 callbacks per second, and HLS 4× at 3.9998×/11.63 callbacks per second with repeated waiting/playing events. These independent picture and audio observations support avoiding native HLS trick-play for eligible fast clips. They do not guarantee every encoding, rate, site or output route.

Local evidence: `audio-local-summary.json`, `hls-audio-local-summary.json`, `audio-recorded-phone-native-closed-root-mp4-pitch.json`, `hls-positive-control-report.json` and the corresponding `audio-system-recording`/`hls-audio-positive-control` XCTest results. The generated recording sources and local-only analysis page are retained with these ignored QA artifacts.
